# 决策点

- 决定：2026-09-04 起，Electron `app.requestSingleInstanceLock()` 是桌宠制作台生产单实例的唯一权威；旧自写文件锁只保留在 `diagnostics/instance-lock/` 供历史复盘，不进入默认包或日常回归。Windows RETURN 使用明确 `paused` 状态表达用户暂停，证据结构有效与产品验收通过分开；历史 `failed` 回传不重解释，跨源码/候选/契约/环境不自动继承通过结论。

## D-001 共享内核与单宠导出

- 决定：维护一套共享运行内核，每只宠物只提供标准宠物包和产品构建配置；单宠独立安装包由构建工厂生成。
- 原因：避免为每只宠物复制和维护完整 Electron 工程。

## D-002 Wukong 0.1.9 作为体验参考基线

- 决定：只读复用 Wukong 0.1.9 的透明窗口、拖动、24 FPS 左右跑步、缩放、托盘、随机动作和长待机经验。
- 原因：该版本已有 source、win-unpacked 和 installed-mode Windows 证据。
- 边界：不修改 Wukong 交付目录；通用项目使用新目录和新身份。

## D-003 两种输入共用下游流程

- 决定：输入 A 为 Petdex v1/v2 包；输入 B 为客户提供的角色素材。两者最终统一为标准宠物包并共用运行、构建和验收流程。
- 原因：移植和新素材制作的差异主要在上游，运行与交付应保持一致。

## D-004 客户素材制作最后测试

- 决定：先完成通用内核、Petdex 移植和单宠导出，再加入客户素材制作测试。
- 原因：当前没有客户测试素材，且 AI 动作生成会引入额外视觉变量，不应阻塞基础技术链路。

## D-005 当前暂缓商业发布体系

- 决定：当前不建设收款、订单、账户、DRM、激活码、商店、正式签名、公证和自动更新。
- 原因：项目处于学生试验阶段，优先验证工具和业务需求。
- 保留：产品 ID、版本、来源、作者、授权状态和哈希等低成本兼容字段。

## D-006 原始素材不可原地修改

- 决定：Wukong、Petdex 和客户原始输入都按不可变来源保存；转换、修复和构建使用版本化派生副本。
- 原因：保证回溯、视觉确认和哈希证据可靠。

## D-007 Phase 1 工具链

- 决定：共享内核使用 Electron 43.4.1、electron-builder 26.15.3，项目 Node.js 下限为 22.12.0。
- 原因：Electron 44 刚进入新主版本且已移除 macOS 12 支持；43.4.1 是仍在维护的成熟版本。electron-builder 使用 npm 当前稳定版。
- 边界：Phase 1 只验证 source-mode；Windows/macOS 构建参数和签名策略在 Phase 3 单独确认。

## D-008 产品选择与素材隔离

- 决定：运行器只接受 `config/products/<selector>.json` 中的白名单产品选择器；配置引用被 Git 忽略的 `local-pets/` 工作副本。
- 原因：换宠物无需改核心代码，同时避免修改或提交 Wukong/Petdex 原始素材。
- 边界：正式导入、来源快照和哈希清单由 Phase 2 实现。

## D-009 Phase 2 安全导入与证据格式

- 决定：目录、ZIP 和 Petdex slug 共用同一标准化管线；每次成功导入保存来源快照、标准包、JSON/Markdown 报告、SVG 联系表和离线动作预览。
- 原因：让来源、哈希、运行输入和视觉证据保持同一版本，避免手工复制后无法追溯。
- 安全边界：所有输入均不可信；拒绝链接与路径逃逸，限制数量和体积，使用临时目录加原子改名，输出目录由来源和内容摘要区分且不覆盖。

## D-010 Petdex slug 采用隔离直连适配器

- 决定：不调用会写入 `~/.petdex/pets/` 和 `~/.codex/pets/` 的 Petdex CLI 安装命令；从固定官方清单读取 slug，只接受 `assets.petdex.dev` 的受信清单、JSON 和 WebP，再写入临时隔离目录。
- 原因：满足内部 slug 导入需求，同时保护用户现有宠物目录并复用统一校验与哈希流程。
- 边界：只有 slug 获取阶段需要网络；导入后的标准包和运行器保持离线。

## D-011 Phase 3 候选构建范围

- 决定：Phase 3 生成 Windows x64 `win-unpacked`、未签名 NSIS 候选安装包和 macOS Apple Silicon 未签名 `.app`；不生成 DMG，不执行签名、公证或发布。
- 产品范围：Wukong、Doraemon、阿岱为三个主候选，JokeBear 为额外 v2 内部兼容样本；首轮使用通用测试图标。
- 验收边界：Mac 可完成 source、macOS app 与 Windows 产物静态验证；Windows 真实安装、卸载、重装和 100%/125%/150% DPI 必须在另行授权后完成。

## D-012 Windows 正式验收顺延

- 决定：当前没有 Windows 环境，Phase 3 遗留的 Windows source、win-unpacked、installed mode、卸载/重装和 DPI 正式验收顺延到 Phase 4 完成后统一执行。
- 边界：顺延不改变候选状态；Mac 构建、静态哈希或 Phase 4 完成均不能替代 Windows 正式报告。

- 确认：镜像左跑于 2026-08-28 获用户确认；九种标准动作确认门关闭。后续方向制作范围由 D-016 的 v1 收尾决策取消。

## D-016 小福猩 Phase 4 按 Petdex v1 收尾

- 决定：2026-08-28 用户确认小福猩只对齐 Petdex 网站宠物的核心九状态功能，最终标准包使用 8×9、1536×1872 的 v1 契约，不制作四个基准方向和 16 个注视方向。

- 决定：Windows 验收固定使用 T7 新目录 `小福猩桌宠/xiaofuxing-v1-windows-acceptance-20260828-01/` 中的精确 source ZIP、`win-unpacked` 和未签名 NSIS，不覆盖旧交付或重新构建候选。

## D-019 动态 DPI 不使用临时窗口边界脉冲

- 决定：0.1.2 的 Windows 动态 DPI 路径只执行防抖后的单次稳定逻辑边界同步与表面失效，不再用 `y - 1 / height + 1` 再恢复的临时窗口变形强制重绘。
- 原因：0.1.1 在 150% 冷启动正常，但真实动态 125% 切到 150% 时出现白窗和裁切；日志证明失败紧邻边界脉冲，而历史通过动态 DPI 的实现只做稳定尺寸同步。
- 保留：冷启动首帧后的独立透明表面重绘脉冲继续保留，因为 0.1.1 的 150% 冷启动已经实机通过。
- 防复发：自动测试禁止动态 DPI 回调再次调用边界脉冲；Windows source 的真实动态缩放被提升为安装前最早 GUI 终止门。

## D-020 机器级 NSIS 只精确匹配已安装主程序

- 决定：0.1.3 的机器级 NSIS 运行检测只按 `$INSTDIR\${APP_EXECUTABLE_FILENAME}` 完整路径、大小写不敏感匹配，不再用安装目录前缀覆盖卸载器、`elevate.exe` 或其他同目录进程。
- 原因：0.1.2 覆盖安装弹窗保持期间，同款安装目录进程查询为 0，完整进程表、启动项和计划任务均无小福猩进程，证据支持 NSIS 检测误判而非旧开发版冲突。
- 边界：仅机器级产品启用该 include；用户级产品保持原策略。查询异常只记录诊断并交由后续文件锁/卸载结果兜底，不等同于安装通过。
- 复验：保留 appId、EXE 名、安装范围和用户数据身份；Windows 只重验 `0.1.0 -> 0.1.3` 覆盖安装、installed mode、官方卸载与干净重装。

## D-021 0.1.5 仅关闭卸载器 CRC 自检

- 决定：在 `BUILD_UNINSTALLER` 编译分支对 0.1.5 卸载器设置 `CRCCheck off`；主安装器继续保留并通过 CRC 自检。
- 原因：electron-builder 26.15.3 在 macOS 上通过 `UninstallerReader` 拼接卸载器时不执行 NSIS `WriteUninstaller` 的 stub 修正，也不重算 CRC，导致未损坏的卸载器稳定触发错误自检；静态复算和 Windows `/NCRC` 对照均确认该根因。
- 边界：不改 node_modules、appId、EXE 名、机器级安装范围、安装路径、卸载入口、用户数据身份或批准素材；0.1.4 的诊断探针与预检宏全部保留。
- 验收：0.1.5 主安装器 CRC 一致，卸载器结构完整且仅设置 NO_CRC；Windows 三次同版本覆盖、官方卸载（不带 `/NCRC`）和同包重装通过。

- 决定：应用内候选构建不再直接把 `ELECTRON_RUN_AS_NODE=1` 指向 electron-builder CLI，而是经 `src/workbench/builder-launcher.js` 中转：规范化 `process.argv`（对齐 yargs 17 `hideBin` 对 Electron 形态的裁剪）、设 `process.noAsar = true`（避免 ASAR 补丁拦截 builder 对 `default_app.asar` 的写入）、校验 CLI 路径必须等于受控 builderRoot 内的固定位置后再 `require`。

- 配套：`resolvePreviewSpawnCwd` 在任何 stat 之前按 basename `app.asar` 判定（Electron ASAR 补丁会把 app.asar 报成目录）；工作台主进程读取候选 `app.asar` 的检查器与 manifest 哈希使用局部 `process.noAsar` 开关（不同步全局关闭，`main.js` 仍依赖 asar 读取渲染入口）；验证器 `--output` 拒绝 RETURN 内路径，validator 输出不再进入 checksum 闭环。
- 证据：`-09` RETURN 复核、222/222 全量回归、macOS 候选 `candidate-20260902153954972` packaged smoke（`Resources/phase-6.6-workbench-evidence.md` 本轮小节）。
