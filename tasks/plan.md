# PRD 与实施计划：通用桌宠工作流

## 问题

Petdex Desktop 可以脱离 Codex 运行，但下载和社区依赖网络环境。当前 Wukong 成品证明独立 Electron 桌宠可行，却把角色、图集和产品配置写死。项目需要把这套经验转化为离线、配置驱动、可重复生产多个桌宠安装包的工作流。

## 成功标准

- 同一运行内核可加载 Wukong、v1 `doraemon` 以及 v2 `dai`、`jokebear-codexpet`，核心代码不因换宠物而修改。
- 安装后的宠物不依赖 Codex、Petdex、VPN、账户或运行时网络。
- 导入器能够识别 v1/v2、校验输入、保存来源与哈希，并拒绝结构不完整或不安全的包。
- 每只宠物可通过产品配置生成独立名称、图标、appId/bundleId、版本和数据目录。
- Windows 与 macOS 构建和验收结论分开记录；未签名产物只称测试版或候选版。
- 客户素材流程最终支持至少一张清晰、完整、无遮挡的全身正面图，允许 AI 辅助，并在角色基准、动作、注视方向和最终效果处人工确认。

## 当前范围

包含：

- 共享离线桌宠运行内核。
- Petdex v1/v2 的本地目录、ZIP 和内部 slug 下载导入。
- 自动校验、标准化、预览和不可变来源记录。
- 配置驱动的单宠 Windows/macOS 构建。
- 客户素材制作流程的最后阶段验证。

不包含：

- 收款、订单、账户、DRM、激活码和在线商城。
- Windows 商业签名、macOS Developer ID、公证和正式商店发布。
- 自动更新、遥测、广告和运行时云服务。
- 未取得商业授权的社区宠物对外分发。

## 约束

- Wukong 交付目录和 Petdex 原始安装目录只读。
- 支持 v1 1536×1872 与 v2 1536×2288；版本识别同时参考声明和真实尺寸。
- 来源 slug、`pet.json.id` 和最终产品 ID 必须分开，避免覆盖与身份冲突。
- 导入和构建输出必须版本化，不覆盖历史结果。
- 真实透明窗口、拖动、缩放和动态动作验证是独立质量门。
- 客户素材缺失不阻塞 Phase 1–3。

## 架构方向

- `pet-package`：统一宠物包契约，保存来源、身份、图集、状态、版本和哈希。
- `pet-validator`：解析目录/ZIP，识别 v1/v2，检查路径、尺寸、alpha、JSON、帧和边界。
- `pet-importer`：只负责获取和复制到隔离工作区，不修改来源。
- `runtime-core`：窗口、渲染、交互、状态机、设置和日志，不包含角色文案与路径。
- `product-profile`：产品名、appId/bundleId、图标、默认宠物、版本和构建目标。
- `build-factory`：根据产品配置生成版本化候选安装包和清单。
- `customer-intake`：最后接入素材登记、角色基准、动作生成、视觉确认和标准包输出。

### Phase 2 威胁模型与安全边界

- 不可信输入：本地目录树、ZIP 条目和元数据、`pet.json`、图集字节、Petdex slug 与 CLI 输出。
- 受保护资产：项目外文件、原始宠物目录、历史导入结果、标准宠物包身份与哈希证据。
- 主要风险：路径穿越、符号链接逃逸、覆盖、资源耗尽、命令注入、身份冲突和不完整输出被误当成成功导入。
- 控制：允许列表、真实路径边界检查、文件数/单文件/总大小限额、无 shell 子进程、临时目录与原子改名、版本化非覆盖输出、明确错误代码。

## 主要风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| Wukong 代码高度硬编码 | 换宠物仍需改源码 | 先定义包契约和产品配置，再迁移行为 |
| v1 缺少 v2 注视方向 | 行为不一致 | 明确状态能力与回退策略，不伪造方向帧 |
| slug 与包内 ID 冲突 | 覆盖、数据混用 | 来源 slug、宠物 ID、产品 ID 分离并校验 |
| 旧 Electron 依赖公告 | 安全与维护风险 | 新项目实施前单独确认工具链并完整回归，不直接复制旧依赖 |
| macOS 不能证明 Windows | 错误发布结论 | 平台证据分开，真实 Windows 验收后再升级状态 |
| AI 生成动作身份漂移 | 客户返工 | 最后阶段执行，角色基准和逐阶段确认作为硬门 |
